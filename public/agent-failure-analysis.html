六档思考强度（关闭 / 自动 / 极低 / 低 / 中 / 高）在 UI 上真实可选，选项也确实传到了后端， 但出站请求体里没有任何 effort 字段——一档都没生效。

根因是一次 Harness 层的契约断裂：能力声明层 （Capabilities()）按「missing key = 支持并原样透传」的语义虚报了六个档位； 请求编码层（applyThinking()）对 chat-template-kwargs 线格式 只能表达一个布尔。两方各说各话，中间没有任何一方报错。

修复让能力声明层只承诺编码层真正能表达的东西，并补齐 opt-in 路径下的 effort 编码。 已合入上游 main；同一 issue 下另一份竞品 PR 被维护者以 Closing in favour of #3552 关闭。

一

执行过程

环境是 WeKnora 官方 main 镜像（d6c7665c）、Docker Compose 部署， 模型行走中转站（DMXAPI，OpenAI 兼容网关）+ glm-5.3——一个混合推理模型。 症状很难直接归因：没有错误、没有异常栈，只有「agent 的行为和配置对不上」。 这正是 agent harness 类缺陷里最难查的一种。

    查请求预览（handler/model.go:448），抽屉发出的 options.reasoning_effort 确实分别是 minimal / high。 选项已经正确到达后端——问题被夹在「后端收到选项」和「出站请求编码」之间。

  4. 对照实验：把责任锁死在本地编码层

    保持 url / key / 模型完全不变，只把该模型行的 provider 从 generic 改成 zhipu， 档位差异立刻出现在 wire 上。再跑 58 份 dump 做统计：wire 上只出现过 low / high / max 三个值（目录里的 per-model ladder 把 minimal→low、medium→high、xhigh→max 折叠），即六档 UI 实际只有三组 wire 配置。 按 wire 值重新分组后，思考量与耗时严格单调：

applyThinking 的 chat-template-kwargs 分支只写 enable_thinking 布尔； 且 generic 的 SupportsReasoningEffort 默认 false， if enabled && level.Graded() && s.SupportsReasoningEffort 不成立， effort 根本不被计算。

缺陷的本质

Supports() 的 missing-key 语义本身是合理的——它服务于「已收录但未列全档位」的 vendor。 问题出在能力声明层直接复用了这个语义，去回答一个它回答不了的问题： 「这条链路能让用户选这个档位吗？」回答它需要同时知道线格式能表达什么，而 Capabilities() 只看 vendor map。这是典型的契约信息缺失。

对 agent harness 而言这类缺陷格外危险：思考强度直接决定每一轮 ReAct 的 token 消耗。 能力层虚报档位，等于告诉用户「你可以控制成本与延迟」，而 agent 永远跑在最高推理强度上—— 成本预算、延迟预期、乃至任务能否跑完，全部失控。
三

修复方案

方案 A（PR 主体）：能力声明层只承诺可表达的东西

在线格式是纯布尔开关、且未 opt-in supports_reasoning_effort 时， Capabilities() 出口只保留非 graded 档位（off / auto）：

internal/models/runtime/resolve.go
caps.ThinkingLevels = r.ThinkingLevels.SupportedLevels()
+ // A chat-template switch carries only the enable_thinking boolean: every
+ // graded rung is silently dropped on the wire (and a relay backend that
+ // does not know enable_thinking drops the boolean too), so the selector
+ // must not offer rungs the request cannot express. Vendors that opt into
+ // a top-level effort field keep their ladders (#3489 moved its NIM
+ // entries to that shape).
+ if r.API == api.APIOpenAICompletions &&
+ r.OpenAICompletions.ThinkingFormat == api.ThinkingFormatChatTemplateKwargs &&
+ !r.OpenAICompletions.SupportsReasoningEffort {
+ keep := make([]api.ReasoningEffort, 0, 2)
+ for _, level := range caps.ThinkingLevels {
+ if !level.Graded() {
+ keep = append(keep, level)
+ }
+ }
+ caps.ThinkingLevels = keep
+ }
  • 保留 off / auto：enable_thinking:false 对 Qwen 系 vLLM / SGLang 自托管模型是真实开关（generic 的本义场景），砍掉会误伤；Capabilities() 无法知道后端是谁，只保留布尔能表达的两档。
  • 条件里带 !SupportsReasoningEffort：只收敛纯布尔场景，不误伤「format=chat-template-kwargs 但 effort 走顶层」的组合（#3489 给 NVIDIA NIM entry 选的就是这个形状）。
  • vendor map 不动：修的是出口而不是事实来源，跨厂商目录不受影响。

方案 B（review 后提前兑现）：opt-in 时把 effort 写到 wire 上

原本作为「方向 2」放在 issue 里讨论——让显式选择 graded 档时同时上行顶层 reasoning_effort。依据是 vLLM 文档明确接受与本项目相同的 ladder 并据此注入 enable_thinking。

维护者在 review 里把它提成了合并条件，因为他抓出方案 A 的一个自相矛盾： 我在注释里为「未来组合」留了 !SupportsReasoningEffort（capabilities 保留 ladder）， 但 applyThinking 的对应分支仍然不发 effort——于是那个组合 依然是每档请求体逐字节相同，同一个缺陷换了个形状活着。

internal/models/api/openaicompletions/request.go · 6ddf571a
case api.ThinkingFormatChatTemplateKwargs:
body["chat_template_kwargs"] = map[string]any{"enable_thinking": enabled}
+ if effort != "" {
+ body[effortField] = effort
+ }
这次 review 迭代比修复本身更有价值：我预留的「未来组合」被证明不是一个未来问题， 而是当下就存在的同源缺陷——出口收敛必须与编码路径成对修改，只改一边就是把 bug 藏起来。

方案 C（issue 中讨论，不做实现）

provider=generic 时按模型名跨全目录反查，命中则提示或借用 catalog 事实，降低中转站用户 「必须知道要选官方 provider」的知识门槛。风险是 relays 可能挂羊头卖狗肉（模型名 ≠ 实际后端）， 属于新的越权猜测，需要产品侧决策，因此只作为长期 UX 方向记录。
