一、开源贡献 · Tencent/WeKnora（34.1k star 开源 RAG / Agent 平台）

排查起点：同一套 ReAct agent 在 GLM-5.3、DeepSeek-V4.1-Flash 下出现答案不生成、思考死循环、重复渲染卡死，而 Qwen 一切正常。结论不是"智能体没针对模型调优"，而是harness 工程缺陷被特定模型行为触发——共定位 5 项根因，全部附可复查的 upstream 链接。

1. 思考强度档位在 Harness 层被静默丢弃　✅ 已合入上游

配置页提供六档思考强度，选项也确实传到后端，但 wire 层只发出一个 enable_thinking 布尔，六个档位一档都没生效；对不认识该布尔的中转后端，"关闭"档同样是谎言选项。根因是能力声明层（Capabilities()）按"missing key = 支持"的语义虚报档位，而请求编码层只能表达一个布尔，两方各说各话且都不报错。

本人贡献：#3551 独立发现并完成四层取证（行为 A/B → UI 请求预览 → wire 逐字节对比 → 同 url/key 的 provider 对照实验）；实现 #3552 并被维护者 squash merge 进上游 main（commit a9d71038，4 files +114 行，含 4 个先红后绿测试）；review 轮响应维护者指出的 opt-in 组合不一致并当日修复；同 issue 的撞车 PR #3628 被维护者关闭（Closing in favour of #3552）。

  • PR（merged）：https://github.com/Tencent/WeKnora/pull/3552
  • Issue：https://github.com/Tencent/WeKnora/issues/3551
  • 📎 完整失败分析（执行过程 / 根因判断 / 修复方案 / 验证结果）：failure-analysis-thinking-levels.html

2. 前端答案跨轮堆叠与浏览器卡死　✅ 修复方案与本人一致并被上游采纳

ReAct 每轮新建 answer 事件时会继承上一轮事件的全部文本再追加，叠加打字机"目标变短即归零重打"与每帧全文 markdown 重解析，导致答案反复从头渲染，第 N 轮接近立方级工作量，最终主线程饱和、窗口无响应。

本人贡献：issue #3383 提出者——根因分析被采纳，上游修复 PR 与本地方案逐字符一致；在 #3386 担任独立验证者（A/B 实测"卸下守卫 5/5 堆叠 vs 装回 0 复制"、守卫日志取证 38512 字符恶劣场景），归因部分被作者写入 PR 描述。

  • 上游落地：https://github.com/Tencent/WeKnora/pull/3386（squash 30171451）
  • 本人报告：https://github.com/Tencent/WeKnora/issues/3383

3. 快速问答 length 静默截断：零答案、零错误　✅ 已闭环

混合推理模型的思考 token 与正文共享同一预算，思考烧尽预算后 finish_reason=length、answer 通道为空，但整条链路对 length 零检测——发一个空事件即标记"正常完成"，用户看到"已引用 2 篇文档"后没有下文。

本人贡献：issue #3509 提出者（file:line 根因链 + A/B 对照证据，后被证明是社区实现 PR 的蓝本）；PR #3515 由社区贡献者按该规格实现并当日合并，本人完成 post-merge 真机验证（兜底文案出现、truncated:true 全链路落库生效）与 diff 复审，发现 fallback 路径的同款缺口。

  • 本人报告：https://github.com/Tencent/WeKnora/issues/3509
  • 社区实现：https://github.com/Tencent/WeKnora/pull/3515（merged 78d7d862）

4. GLM/Zhipu 无 provider adapter，无法关闭思考　✅ 上游已以更深方案落地（本人独立推导一致）

provider 注册表没有智谱适配，请求落到默认的"什么都不发"策略，模型默认持续思考；而智谱对"关闭思考"直连会报 1210 错误——这是一个没有正确配置可抄的跨厂商契约问题。

本人贡献：本地复现 1210 + 官方 API 五组 curl 实测定参，独立推导出"off 映射 null、永不发 disabled"的设计；上游 #3470/#3489 以 vendor 层重建落地后，本人完成真机验证（目录命中、off:null 生效、thinking-format 正确）；并由此延伸发现 provider=generic 的存量迁移陷阱（见第 1 条）。

  • 上游实现：https://github.com/Tencent/WeKnora/pull/3470

5. 截断答案"续写"，但前半部分丢失　🔍 已定位（上游以终止方案覆盖）

length 不被视为自然停止，半截答案进入消息历史，模型下一轮自发"补全剩余内容"——但前端把第一轮答案当 preamble 标记 superseded 丢弃，模型看得到前半部分，用户看不到。

本人贡献：定位完整机制链（length 非自然停止 → 截断答案进历史 → preamble 被丢弃），并作为 #3362 现场证据的独立佐证；上游以"终止本轮 + 截断标记"方案覆盖，本人转 post-merge 验证。

二、Agent Demo · 山野游伴：动物园智能游伴 Agent

仓库：https://github.com/DerrickLinus/zoom-champion-agent　|　FastAPI · Qwen · React 19 · NetworkX

项目背景

南京红山森林动物园是国内少数坚持不靠动物表演、以动物福利为经营底线的城市动物园，因此面对传统景区共有的可持续性困境：客流成倍增长，人力密集型讲解无法承载；而园区真正有价值的内容——公众号文章、场馆讲解词、饲养员的日常记录——散落在各处，游客无法深度体验这些故事。

项目简介

「山野游伴」用一句话解决上述矛盾：用户说"我带着 3 岁孩子，只有 2 小时，怕晒，不想爬山，想看灵长类"，它就规划出约束内的路线并解释为什么这样安排；游中说一句"累了"或"这个馆太挤了"，实时调整剩余行程；到馆后由人格化"动物搭子"讲解并支持语音问答；整条路线还能变成一场边走边玩的互动故事。

核心设计主张：不让大模型编造路线。 LLM 只负责它擅长的两件事——理解（自然语言 → 结构化需求）与表达（解释、讲解、叙事）；流程调度由确定性 Orchestrator 状态机完成，路线在加权拓扑图（14 节点 / 20 边，含距离、坡度、遮荫率、拥挤度）上用 Dijkstra + 贪心插入计算。

运行效果
